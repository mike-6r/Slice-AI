# Slice feature compatibility matrix

This matrix compares every real (non-Infria-specific) capability inventoried in
`OLD_BOT_FEATURE_INVENTORY.md` against Slice's actual, verified backend state as documented in
`docs/backend-build-guide/` (summarized in `CURRENT_STATE.md` of this build guide). Status vocabulary
follows the source documents exactly: **VERIFIED/COMPLETE** (built and tested), **PARTIAL**
(implemented, one QA gate open), **NOT STARTED**, **DEFERRED** (blocked on external approval).

| Old feature (generic pattern) | Old behavior | Current Slice backend support | New API needed? | Bot-side adapter sufficient? | Conflicts with current security rules? | Migration action | New design |

## Net assessment

Every Infria-specific feature (gang/faction system, Tebex store) has **zero** Slice backend
counterpart and is REMOVE. Every generic Discord-community feature (tickets, moderation, giveaways,
suggestions, error handling, embed patterns) has **zero direct Slice API dependency** and can be
REWRITE'd as bot-owned functionality using modern Discord primitives, independent of Slice's build
timeline. The one feature with a genuine conceptual echo in Slice's real backend (the
trailer-approval DM/react workflow ↔ Slice's real submission-review workflow) must **not** be
migrated as "let Discord reactions decide the outcome" — Slice's own reviewer-separation and audit
model already owns that decision, and the bot may only ever become a *read/notify* surface for it,
gated on Doc 017 shipping.

See `BOT_PRODUCT_SPEC.md` for the client's newly-requested feature list run through the same
reality-check treatment (most of it maps to Slice backend phases 012–017, which are NOT STARTED or
DEFERRED today).
